# 下一阶段实施计划与模型交接

当前阶段交付方案、内容/依赖研究与开发基线；业务功能仍以 SPEC 状态为准。最终系统是自家 Mac Studio 的 B/S 应用，浏览器经家庭局域网 HTTPS 使用课程、进度和本地评分，录音评分后丢弃且不发送第三方。可断互联网运行，不承诺 Mac 停机后浏览器独立学习/评分。

## 2. 最小任务单位

每个 SPEC 再拆成 3–6 个小提交：契约/fixture → 纯函数或 adapter → API/存储 → 页面 → 故障与验收。每次给模型一个切片、一组文件边界、一组验收案例；避免同时要求它重做架构、选模型和实现全产品。

每个提交说明：解决哪个 R-ID、行为如何改变、跑了哪些命令、仍有什么未验证。格式与 git 规则遵循 `AGENTS.md` 及工程 workflow。无需为纯可逆样式变化新增机械测试；重要算法、输入边界、并发、数据删除和资源清理必须有针对性验证。

## 3. 通用实施提示模板

```text
阅读 AGENTS.md、docs/product/PRD.md、docs/product/UX.md、docs/architecture.md、
docs/api-contract.md 和 docs/specs/SPEC-00N-*.md，检查当前契约和已有代码。
仅完成该 SPEC 指定切片，不更改技术栈、教学规则或引入第三方语音服务。
先列出当前状态与最多 6 个小步骤，然后直接实施已授权的软件工作。
ID 和课程顺序来自 content；前端类型与服务端 OpenAPI 保持一致。
先满足 Given/When/Then，再补适当 UI；错误/取消/恢复必须与正常路径同时实现。
运行 npm run verify、npm run verify:server，并按切片运行 npm run test:e2e。
更新该 SPEC 状态与证据，说明外部依赖，不伪造音频、评分或真机结论。
给出改动文件、测试结果和明确下一切片；按规范独立提交，不主动推送发布。
```

对 SPEC-000 使用该文件的研究提示，不能沿用「只写代码就能完成」模板。对 003 的提示必须附 000 通过报告、冻结模型/校准版本和音频清单；缺任何一项，软件可局部进行但不得完成验收。
